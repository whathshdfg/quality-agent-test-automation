# Quality Agent Studio：需求驱动的智能测试工作台

> Atoms-Demo 笔试项目说明。当前版本是 `quality-agent` 的独立网页演示层，围绕“业务需求 → 结构化测试资产 → 覆盖分析 → 定向补充”提供可操作的产品流程。

## 1. 项目定位

Quality Agent Studio 面向测试工程师、产品经理和开发人员，帮助团队将自然语言需求转化为可评审、可编辑、可导出的测试资产。

以订单支付为例，一段需求往往同时包含订单状态约束、支付成功后的数据更新、重复支付处理和异常响应。工作台将这些内容拆解为需求规则和测试点，生成测试用例，再展示哪些维度缺少覆盖，支持用户定向补充。

本项目选择软件质量保障作为垂直场景，希望缩短“读懂需求”到“形成测试方案”的距离，并使生成结果能够被人工审阅和修正。

## 2. 与挑战要求的对应关系

| 挑战要求 | 当前实现与完成情况 |
| --- | --- |

| 真实交互 | 支持任务创建、示例加载、用例编辑、筛选、删除、复制、状态标记和导出 |

## 3. 已完成的功能

### 需求输入与任务初始化

- 输入任务名称、业务类型和自然语言需求，选择风险关注标签。
- 对任务名称和需求正文进行基础校验。
- 支持业务类型自动识别，并内置支付、订单取消、用户登录、订单创建四类示例。
- 工作台展示任务数量、用例数量、平均覆盖率和 P0 用例数量。

### 测试资产生成与管理

- 将需求拆解为结构化规则，展示规则类型、风险级别和关键词。
- 生成测试点和测试用例，通过关联规则 ID 支持回溯。
- 用例包含标题、优先级、前置条件、测试步骤、预期结果和执行状态。
- 支持新增、编辑、复制、删除用例，按标题或维度搜索，按优先级和维度筛选。
- 支持人工标记“未执行／已通过／已失败”。这些状态是用户记录，不代表系统执行了真实测试。

### 覆盖分析与定向补充

- 展示规则、功能流程、参数和风险四类覆盖指标。
- 对缺失维度给出风险说明和补充建议。
- 支持补充单个维度，或一键补齐全部可识别缺口。
- 修改用例后重新计算覆盖结果，形成“生成 → 评审 → 补充”的反馈流程。

覆盖率表示本地规则模型中的测试资产关联情况，不是代码覆盖率、真实测试通过率或完整质量保证。当前按维度判断测试点覆盖，同一维度存在用例即可标记该维度下的测试点；综合覆盖率为四类指标的算术平均，没有适用项的分类按 100% 处理。因此，高覆盖率仍需人工检查用例内容是否充分。

### 保存与交付

- 自动将任务及编辑结果保存到当前浏览器 localStorage。
- 支持从历史任务重新打开结果，以及删除任务。
- 支持导出 Markdown 报告和 JSON 数据，便于评审和后续处理。
- 提供窄屏导航入口和适配样式。

## 4. 实现思路与关键取舍

### 先完成可操作的垂直流程

第一阶段围绕测试工作的实际操作组织界面：输入需求、查看规则与测试点、编辑用例、识别缺口、补充并导出。用户可以修改生成结果，数据与指标会随操作变化，而不是仅观看静态展示。

### 使用可解释的本地规则引擎

生成流程由需求分析、测试点生成、用例生成、覆盖计算和缺口补充模块组成。系统根据需求文本中的关键词及风险标签识别状态约束、参数校验、数据一致性、权限安全和并发幂等等信息。

该方案无需模型密钥或外部请求，便于在演示环境中快速体验，也便于验证输入、规则与输出的关系。代价是自然语言理解能力有限，复杂业务可能存在误识别或遗漏，用例内容仍需人工评审。

当前模块划分为后续替换生成实现提供了位置，但本地顺序调用本身不构成多智能体系统。

### 独立前端与浏览器持久化

前端位于仓库根目录下的 `atoms-demo/`，具有独立依赖和构建命令。现有项目包含 Python、FastAPI、LangGraph、SQLite 和 SSE 能力，当前 Demo 尚未调用这些后端服务。

localStorage 降低了第一阶段的部署成本，任务无需登录即可保存。其边界是数据仅属于当前浏览器和站点，无法跨设备同步，也不具备团队协作、服务端备份和权限控制。清除浏览器数据会丢失记录，可通过导出保留副本。

### 技术选型

| 技术 | 用途与选择理由 |
| --- | --- |
| React + TypeScript | 实现交互界面，并约束任务、规则、测试点和用例的数据结构 |
| Vite | 提供独立开发服务和静态构建流程 |
| React Router / HashRouter | 组织工作台、历史任务和任务详情，使用 hash 路由减少静态托管的路由配置需求 |
| Lucide React + CSS | 提供界面图标和样式，控制依赖与界面实现成本 |
| localStorage | 满足第一阶段单浏览器持久化需求 |
| Vitest | 验证规则识别、用例生成、去重、覆盖计算、补充、存储降级与报告导出 |

## 5. 推荐体验流程

1. 打开应用，进入“示例需求”，选择支付示例并生成任务。
2. 在“需求规则”中检查状态约束、重复支付及数据一致性规则。
3. 查看“测试点”和“测试用例”，编辑一条用例的步骤或预期结果。
4. 在用例列表中搜索“幂等性”，删除该维度的全部用例，使该维度形成覆盖缺口。
5. 进入“覆盖分析”，查看缺失维度及建议，补充该维度用例，观察覆盖结果变化。
6. 将一条用例人工标记为“已通过”，刷新页面，从历史任务重新打开并确认编辑内容和状态仍在。
7. 导出 Markdown 报告或 JSON 数据，检查下载内容。

首次访问不需要注册或模型 API Key。不同浏览器、不同站点地址之间的任务数据相互独立。

## 6. 本地运行与验证

在 `quality-agent` 仓库根目录执行：

```powershell
cd atoms-demo
npm install
npm run dev -- --host 127.0.0.1
```

打开终端实际显示的地址，通常为 `http://127.0.0.1:5173/`。按 `Ctrl+C` 停止开发服务。

前端测试、构建与构建产物预览：

```powershell
npm test
npm run build
npm run preview -- --host 127.0.0.1
```

原有 Python 回归测试需在仓库根目录、具备项目 Python 依赖的环境中执行：

```powershell
python -m pytest
```

开发阶段已有验证记录：前端 11 项测试通过，前端生产构建通过，原有 Python 测试 174 项通过，另有 1 条依赖弃用警告。这些记录不代表浏览器端到端测试或线上验收；正式提交应对最终提交版本重新检查构建和主要体验流程。

## 7. 当前边界与扩展优先级

| 优先级 | 下一步 | 原因 |
| --- | --- | --- |
| P0：满足核心挑战 | 增加智能体驱动的应用代码生成、受隔离的运行环境和网页预览 | 当前最大差距是尚未具备“生成并展示应用”的能力。可将业务需求转化为一个可交互的业务原型，再用现有测试资产检查其行为 |
| P0：完成交付 | 部署静态 Demo、推送源码并确认 public 访问权限 | 使评审者能够直接体验，并获取对应版本的源代码 |
| P1：真实生成流程 | 接入现有 FastAPI 和 V3 任务接口，使用 SSE 展示真实节点事件，接入真实 LLM | 复用现有异步任务能力，提升需求理解与生成质量，支持失败重试和过程查看 |
| P1：评审可信度 | 将覆盖判断细化到具体测试点、规则及用例内容 | 避免维度级覆盖掩盖遗漏，为补充建议提供更精确的依据 |
| P2：协作与执行 | 服务端持久化、账号权限、版本记录，以及真实接口测试执行 | 支持团队使用和可追溯的执行结果，逐步替代单浏览器演示模式 |

目前未实现账号注册、团队协作、云端数据同步、真实测试执行、LLM 调用和应用代码生成。这些能力均属于扩展计划。
